**Scope note (why 4 tasks stay in one plan):** This is the single release-finalization unit and
the tasks are causally coupled, not merely co-located — splitting would create artificial
cross-plan dependencies and risk leaving the suite red between plans:
- Task 1 (sever `tcltk`/`tcltk2` from DESCRIPTION) is the **root-cause fix** that greens the 4
  `tcltk`-stub tests reconciled in Task 3 — the same change must land together or the suite
  cannot go green.
- Task 3's D-04 won't-verify closure is **documented in the NEWS.md** created in Task 2 (the PICK-03/
  DAT-02 note), so the gate closure and the migration note share one artifact.
- Task 4's source-scan tests directly assert the outputs of Tasks 1–2 (severed DESCRIPTION/NAMESPACE,
  NEWS content); they are the verification half of the same change, not separable work.
All four are light config/test edits (~10–15% context each, ~40–55% total), within the ~50% budget.
Keeping them atomic is what guarantees the phase-gate invariant: `DESCRIPTION` severance and the
full-suite-green reconciliation happen in one wave so the retirement never leaves a broken state.
